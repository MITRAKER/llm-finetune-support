# Contributing

Thanks for helping. This guide explains how to set up the project, which checks
your change must pass, and how a change goes from a branch to a release.

## Set up

You do not need a GPU to work on the code: the tests train a tiny random model on
the CPU.

```bash
git clone https://github.com/MITRAKER/llm-finetune-support.git
cd llm-finetune-support
python -m venv .venv && source .venv/bin/activate   # Python 3.11, 3.12 or 3.13
make install          # dev tools + pre-commit hooks
make test             # fast unit tests
```

For the end-to-end smoke test (about two minutes on a laptop), and for `make check`,
install the CPU training stack too: `pip install -r requirements/smoke.txt`.

Training itself needs a GPU. The easiest way is the Kaggle notebook in
`notebooks/kaggle_pipeline.ipynb`; see the README.

## Make a change

1. Open an issue first for anything bigger than a small fix, so we can agree on the approach.
2. Create a branch from `main`: `git switch -c fix/short-description`.
3. Make the change with tests. Keep functions short and simple (see below).
4. Run `make check`. It needs the CPU training stack (`pip install -r requirements/smoke.txt`):
   it trains a tiny model, and without it the coverage gate fails. The pre-commit hooks
   also run on every `git commit`.
5. Add a line to `CHANGELOG.md` under "Unreleased".
6. Open a pull request. The template asks what changed, why, and how you tested it.

CI runs on every pull request and must be green before merging:

| Job | What it checks |
|---|---|
| Lint | ruff (style, likely bugs, complexity, security rules), ruff format, mypy types, the Power of Ten checker |
| Unit tests | the fast tests on Python 3.11, 3.12 and 3.13 |
| Smoke test | every test, including a real training and evaluation run of a tiny model, with at least 85% coverage |
| Audit | pip-audit: known vulnerabilities in every requirements file (dev, CPU smoke test, GPU training, demo app) and in the Space's Gradio version; it also fails if the GPU pins cannot be installed together |
| CodeQL | GitHub's security analysis of the Python code and the workflows |

## Code standard

We follow NASA/JPL's "Power of Ten" rules adapted to Python. The full table, with
the tool that enforces each rule, is in [docs/CODING_STANDARD.md](docs/CODING_STANDARD.md).
The short version:

- Simple control flow: no recursion, low complexity, functions of at most 60 lines.
- Every loop has an upper bound; no `while True:`.
- No global mutable state: pass data in, return data out.
- Check inputs at function boundaries and raise a clear error that says how to fix it.
- Type hints everywhere (mypy checks them). Zero warnings: the tests turn every warning into an error.
- Heavy libraries (torch, transformers, unsloth) are imported inside the functions that
  need them, so the rest of the code and its tests run without a GPU.

## Experiments

One experiment is one config file in `configs/`. Copy `qwen3_4b_qlora.yaml`, change
it, and run the pipeline with `--config` pointing at the copy. Do not commit data,
model weights or `outputs/`: they are regenerated by the pipeline and `.gitignore`
keeps them out. If an experiment improves the results, open a pull request with the
new config and the comparison table from `results/REPORT.md`.

## Releases

Versions follow [Semantic Versioning](https://semver.org/). To release:

1. Move the "Unreleased" notes in `CHANGELOG.md` under a new version heading, for
   example `## [0.2.0] - 2026-12-01`.
2. Set the same version in `pyproject.toml` (and `CITATION.cff`), and merge.
3. Tag the merge commit and push the tag: `git tag v0.2.0 && git push origin v0.2.0`.

The release workflow checks that the tag matches `pyproject.toml` and publishes a
GitHub release with the notes from the changelog.

## Dependencies

Versions are pinned in `requirements/` so every run uses the same libraries. The
exceptions are bitsandbytes and huggingface-hub in `train.txt`, which are ranges, and
torch on the GPU, which comes from the Kaggle image. Dependabot opens weekly pull
requests for upgrades. CI tests them on the CPU only and never runs Unsloth or
bitsandbytes, so a pull request that changes `requirements/train.txt` also needs a
quick-test run of the Kaggle notebook before you merge it. Unsloth 2026.11.5 caps
torch (<2.15), transformers (<=5.17.0), trl (<=1.15.0) and datasets (<5), so their
upgrades wait for a new Unsloth release. peft and accelerate are not capped, but
Unsloth patches them, so their minor upgrades are also done by hand and tested on a GPU.

The Space installs Gradio from `sdk_version` in `app/README.md`, which Dependabot
cannot see. CI audits that version for known vulnerabilities; to upgrade it, change
`sdk_version` and the version in `tests/test_deploy_space.py` together.

To update the pre-commit hooks: `pre-commit autoupdate`.
